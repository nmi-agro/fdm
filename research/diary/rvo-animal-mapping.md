# RVO animal-detail mapping — "Raadplegen Dier- en Merkdetails" → fdm schema

Source: `Berichtenboek I&R 3.0.7.pdf` (RVO, versie 3.0.7, documentdatum 18-03-2025), chapter 6 "Berichtspecificaties Dieren", message "Raadplegen Dier- en merkdetails" (pages 103–111). This message is a request/reply lookup that returns animal ("dier") and mark/chip ("merk") details for a single animal identified by life number, work number, or health-certificate number; public fields are available for any animal, non-public fields only when `selRelatienummerHouder` identifies a (former) keeper of the animal. Only this one message is mapped here — arrival ("Aanvoermelding"/"Importmelding"), departure ("Afvoermelding"/"Exportmelding"/"Doodmelding"), and birth ("Geboortemelding") messages are out of scope for this document but are referenced where an output field of this lookup corresponds to an action already defined for those events in the dairy plan.

This document maps RVO output fields to `research\diary\dairy-farming-implementation-plan-FINAL.md` §4.1 (`animals`, `animal_arriving`, `animal_leaving`, `animal_assigning`) and §4.1's `herds`. All RVO dates are `Datum`, format `DD-MM-YYYY` (date only, no time-of-day) — fdm's `b_start`/`b_end`/`m_start`/`m_end` columns are `timestamptz`, so imports should normalize to midnight UTC (or the farm's local midnight, matching how other fdm date-only inputs like `b_lu_start` are already normalized) rather than inventing a time component.

## Direct mappings (existing columns)

| RVO field | RVO type/format | fdm target | Notes |
|---|---|---|---|
| `dierLevensnummer` + `dierLandcode` | CHAR 12 + CHAR 3 | `animals.b_id_eartag` | Concatenate as `{landcode}{levensnummer}`, e.g. `NL123456789012`; RVO itself accepts either the split fields or the combined form on input, so the fdm-rvo parser should normalize both directions through one shared helper (see closing note). |
| `dierWerknummer` | CHAR 6 | `animals.b_id_worknumber` | Shorter on-farm working number distinct from the lifetime `b_id_eartag`; farmers commonly use it for day-to-day identification (e.g. on a collar tag). |
| `dierSoort` | Num 2, domain `Raadplegen Diersoorten` | `animals.b_species` (`animalSpeciesEnum`) | RVO's I&R webservice is species-generic (Rund/cattle, Schaap/sheep, Geit/goat, Paardachtige/equine, Hond/dog, …); fdm's dairy plan targets cattle only, so the enum currently has a single `rund` value, extendable without a schema change once/if fdm's dairy scope covers other species. |
| `geboortedatum` | Datum DD-MM-YYYY | `animals.b_birthdate` | Direct 1:1, reparsed to `timestamptz`. |
| `dierHaarkleur` | CHAR 3, domain `Raadplegen Haarkleuren` | `animals.b_coatcolor` | Coat colour, not breed — RVO's cattle records don't carry a breed field in this message at all, so `animals.b_breed` stays a manually-entered, non-RVO-sourced field. |
| `dierGeslacht` | CHAR 1, domain `IRD_IND_GESLACHT` | `animals.b_sex` (`animalSexEnum`) | RVO uses a single-letter male/female code; map to fdm's existing `female \| male` enum values, no new enum needed. |
| `dierCategorie` | Num 3, domain `IRD_DIERCATEGORIEEN` | `herds.b_herd_category` (`animalCategoryEnum`) | Per the plan's "category lives on the herd, not the animal" rule (§4.1), this is **not** stored on `animals` — it drives which herd the `animal_assigning` row points to at import time. This is a deliberate design choice, not a mapping gap. |
| `importdatum` | Datum DD-MM-YYYY | `animal_arriving.b_start` | Only when the animal is new to the farm via import (see `b_arriving_method` below); for animals already tracked in fdm, `aanvoerDatumME` (below) is the more relevant date. |
| `dierHerkomstLandcode` | CHAR 3 | drives `animal_arriving.b_arriving_method` | Set `b_arriving_method = 'imported'` when this is present and ≠ `NL`; otherwise `'purchased'` (domestic) or `'born'` (if `geboortedatum` and the current meldingseenheid coincide with birth — cross-check against the not-yet-mapped "Geboortemelding" message when that scope is picked up). |
| `aanvoerDatumME` | Datum DD-MM-YYYY | `animal_arriving.b_start` (for **this** farm) | This is the arrival date at the current meldingseenheid (farm), distinct from lifetime `importdatum` — use this for `animal_arriving` when the animal is arriving at an fdm-tracked farm, reserve `importdatum` for the animal's original entry into the Netherlands. |
| `afvoerDatumME` | Datum DD-MM-YYYY | `animal_leaving.b_end` (for **this** farm) | Mirrors `aanvoerDatumME` for departure from the current meldingseenheid. |
| `dierEinddatum` | Datum DD-MM-YYYY | `animal_leaving.b_end` | Lifetime end date (death/export), used when the animal leaves fdm entirely rather than just this farm; reconcile against `afvoerDatumME` when both are present (they should coincide for a farm-to-abroad departure). |
| `dierRedenEinde` | CHAR 2, domain `IRD_CODE_REDEN_EINDE_DIR` | `animal_leaving.b_leaving_method` | Map RVO's reason codes onto fdm's existing `died \| sold \| slaughtered \| exported` enum; exact code table isn't reproduced in the Berichtenboek body (referenced as a separate domain lookup, "Raadplegen Domeinen") — resolve the code list against that reference message during implementation rather than guessing values here. |

## Fields with no current fdm equivalent — new columns proposed

| RVO field | RVO type/format | Proposed fdm addition | Rationale |
|---|---|---|---|
| `moederLandcode` + `moederLevensnummer` | CHAR 3 + CHAR 12 | new `animals.b_id_dam` (text, nullable, self-referencing to `animals.b_id_animal`) | Dam lineage isn't in the current plan at all. Resolve the RVO mother eartag to an fdm `b_id_animal` via the same eartag lookup used for the animal itself at import time; if the dam isn't already an fdm-tracked animal, store `b_id_dam` as `NULL` rather than inventing a placeholder animal row purely for lineage — lineage is a nice-to-have, not something that should trigger spurious `animal_arriving` rows. |
| `dierOorsprongLandcode` | CHAR 3 | new `animal_arriving.b_id_origincountry` (text, nullable) | Distinct from `dierHerkomstLandcode` (which drives the born/purchased/imported enum) — "oorsprong" is the country of origin (birth), "herkomst" is the country the animal most recently came from; both are useful for import provenance so both get a column rather than collapsing them into one. |
| `dierKalfdatum` | Datum DD-MM-YYYY | out of scope for `animals` — ties to Layer-3 `animal_calving` | The dairy plan already sketches `animal_calving` as a Layer-3, per-animal action (§4.7, "define now, build with DynAm"); this RVO field should feed that table when Layer-3 is implemented rather than being duplicated as a column on `animals` now. |
| `vlagsoort`, `maatregelCode` (+ `maatregel`, `datumIngang`, `datumEinde` on the flag) | CHAR 240 / CHAR 3, domain `IRD_CODE_MAATREGEL_MRL` | new Layer-3 action `animal_flagging` (`b_id_animal` FK, `b_flag_type`, `b_flag_reason_code`, `m_start`/`m_end`) | Health/measure flags are dated events (a flag applies for a period, e.g. an export restriction), not durable identity — per the asset-action rule these belong in a new action table, not as columns on `animals`. Proposed as Layer-3 (define now, build later) since it's not needed for the M1–M4 milestones. |
| `dierPremiestatus` | CHAR 1, domain `IRD_STATUS_PREMIEAANVRAAG` | not mapped — flagged as a gap, no column proposed | This is an EU premium-scheme application status, not relevant to fdm's nutrient/farm-management scope; recording it would add a column nobody in the current plan's insights (§6) or app IA (§7) has a use for. Revisit only if a future EU-subsidy feature needs it. |

## Not mapped (explicitly out of this document's scope)

`dierAliasLandcode`/`dierAliasLevensnummer`/`dierAliasWerknummer`, `dierTijdelijkLandcode`/`dierTijdelijkLevensnummer`/`dierTijdelijkWerknummer`, `dierVervangenLandcode`/`dierVervangenLevensnummer`/`dierVervangenWerknummer` (mark-replacement history — relevant only if fdm ever needs to track eartag replacement events, not needed for the current milestones), the `merkGegevens` mark-list block (chip/mark inventory, a separate concern from the animal itself), `registratiesEnInstanties` (external registry/portal metadata), and the exportworthiness fields (`indExportwaardigheid`, `aantalEnkelExportwaardigheid`, `aantalDubbelExportwaardigheid`, `codeExportwaardigheid`) — these describe intended/registered export or slaughter status, which is a trade/logistics concern outside the dairy nutrient-and-herd-management scope of the current plan.

## Implementation note: shared eartag/country-code parser

RVO accepts and returns the eartag either as split fields (`dierLandcode` + `dierLevensnummer`) or as one combined string with the country/ISO code prefixed (e.g. `NL12345789012` or `52812345789012`), and the plain 11–12-digit number without any prefix is also accepted on input. Since `animals.b_id_eartag` is a single fdm column, `fdm-rvo` needs one shared parse/format helper for this eartag shape, used by this animal-detail lookup now and by any future arrival/departure/birth message ingestion, so the split-vs-combined logic isn't duplicated or drifts between call sites.
